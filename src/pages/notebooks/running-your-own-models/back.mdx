| Word | What it means |
|---|---|
| LLM | Large language model. The part of an AI agent that reads and writes text. |
| Inference | Running a model to answer requests. The model's weights don't change. |
| Weights, parameter | The numbers a model is made of. Each single number is a parameter. “8B” means about 8 billion parameters. |
| Closed model | A model whose weights are never given out, such as Claude, GPT or Gemini. Only available through an API. |
| Open-weight model | A model whose weights anyone can download and run, such as Llama, Qwen, Gemma, Mistral, gpt-oss or DeepSeek. |
| License | The rules for what you may do with a model. Apache 2.0 and MIT allow commercial use. Some model makers use their own licenses. |
| Hugging Face | A website where most open-weight models are shared. |
| Model card | The page that describes a model: what it is for, how to run it, and its license. |
| Gated model | A model you can only download after accepting its license and using an access token. |
| Precision: BF16, FP8, INT4 | How many bits each number uses: 16, 8 or 4. Fewer bits means less memory. |
| Quantization | Storing a model's numbers with fewer bits, to save memory. It can lower quality, so test it. |
| Mixture of experts (MoE) | A model that uses only part of its weights for each token. All the weights must still be in memory. |
| Token, tokenizer | A token is a small piece of text. The tokenizer cuts text into tokens and joins them back. |
| Prefill | Stage 1 of an answer: reading the whole request at once. |
| Decode | Stage 2 of an answer: writing it one token at a time. |
| KV cache | Notes the model keeps about every token in each conversation, so it doesn't redo work. It lives in GPU memory. |
| Batching, continuous batching | Working on many conversations in one step. Continuous batching adds new ones as soon as there is room. |
| PagedAttention | vLLM's way of storing the KV cache in small blocks, so little memory is wasted. |
| Time to first token | How long a user waits before the answer starts. |
| Throughput | Tokens per second for all users together. |
| GPU, GPU memory | A chip that does many simple calculations at once. Its own memory must hold the weights and the KV cache. |
| Tensor parallelism | Splitting one model across several GPUs in the same machine. |
| TPU, Inferentia, Trainium | Chips made by Google (TPU) and Amazon (Inferentia, Trainium). They need software built for them. |
| Quota | The cloud's limit on how many machines of a kind you may run. GPU quota often starts at zero. |
| On-demand, Spot | On-demand machines are yours until you stop them. Spot machines are much cheaper but can be taken back at short notice. |
| Pay per token | Paying a model service for each token in and out. |
| Batch inference | Sending many requests to a model service at once and collecting answers later, at a lower price. |
| Reserved capacity | Paying a model service by the hour for capacity only you use: Provisioned Throughput on Bedrock and Agent Platform, PTUs on Foundry. |
| Data zone | On Microsoft Foundry, a deployment that keeps processing inside a zone such as the US or the EU. |
| Model retirement | When a model service switches off an old model version. Requests to it then fail. |
| Serving engine, vLLM | Software that loads a model into a GPU and answers requests. vLLM is one of the most widely used open-source ones. |
| OpenAI-compatible API | Accepting requests in the same format as OpenAI's API, such as <code>/v1/chat/completions</code>. |
| `/health`, `/metrics` | vLLM's addresses for “am I ready?” and for its numbers in Prometheus format. |
| GPU node pool | A group of machines with GPUs in a Kubernetes cluster. |
| Device plugin, GPU Operator | The device plugin tells Kubernetes how many GPUs a machine has. NVIDIA's GPU Operator installs it and the other GPU parts. |
| Startup and readiness probes | Checks that tell Kubernetes when a container has started and when it is ready for traffic. |
| `/dev/shm` | Shared memory inside a container. vLLM needs more than the default. |
| KEDA, Karpenter | KEDA adds pods based on numbers such as a Prometheus query. Karpenter adds machines on EKS. |
| KAITO | Azure's AI toolchain operator. An AKS add-on that deploys preset models with vLLM. |
| Fine-tuning | Training an existing model a little more on your own examples. |
| LoRA adapter | A small add-on that changes how a model behaves, without changing the model's own weights. |
| Break-even | The level of use at which your own GPU costs the same as paying per token. |
| Model routing | Sending different jobs to different models, for example easy ones to a small model and hard ones to a large one. |

### Chapter 2, Your turn: how big are the weights?

1. 14 billion × 2 bytes = about **28 GB**.
2. 70 billion × 1 byte = about **70 GB**.
3. 8 billion × 0.5 bytes = **a bit over 4 GB**.
4. About **60 GB** (30 billion × 2 bytes). Only 3 billion are used for each token, but all 30 billion must be in memory.

### Chapter 3, Think about it: which stage takes Botley's GPU time?

Probably stage 1. Botley sends thousands of tokens and gets a short reply, so reading the request is a large share of the work. That is also why the wait before the first word matters so much for Botley.

### Chapter 3, Your turn

### Chapter 5, Your turn: choose the option

| # | Answer | Why |

| 1 | Batch | Nobody needs the answers right away, and batch costs 50% less. |

### Chapter 8, Think about it: why --max-model-len=16384?

262,144 tokens × about 147 KB is about **38.7 GB** of KV cache for a single conversation. That is more than the whole 24 GB L4. vLLM checks this when it starts and stops with an error if even one conversation of the maximum length can't fit. Setting 16,384 tokens (about 2.4 GB each) leaves room for about five full-length conversations, or many shorter ones.
